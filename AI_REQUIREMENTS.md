# Обучаемая проверка игровой локализации — согласованная схема

## Цель

На входе: русский и казахский ARB, ключ и контекст строки, утверждённый игровой глоссарий. На выходе: находки с типом, объяснением и уровнем уверенности; три варианта исправления для содержательных ошибок; итоговый ARB только из решений, одобренных носителем языка. Инструмент должен работать с новыми ARB и не считать исходный казахский файл безошибочным.

## Два независимых контура

1. **Детектор** решает, есть ли ошибка в паре `ru → kk`, определяет тип и приоритет. Он не изменяет перевод. Технические правила `locqa.py` остаются отдельной проверкой плейсхолдеров, ICU, ключей и длины.
2. **Исправитель** получает строку, контекст, утверждённый глоссарий и находку. Он предлагает три действительно разных варианта: естественный игровой, нейтральный и краткий для интерфейса (для длинного текста — альтернативную формулировку). Для каждого сохраняются объяснение, термины и ограничения. Ни один вариант не получает человеческую отметку автоматически.

Контуры можно реализовать отдельными моделями или одной готовой моделью с разными вызовами; обучающие данные, задачи и метрики разделяются. Качество каждого контура проверяется отдельно. Модель, создавшая вариант, не является единственным судьёй этого варианта.

## Данные и проверка носителями

- Оригинальный ARB — полевой материал с возможными ошибками, не эталон.
- Только явно принятая носителем строка попадает в эталон: `key`, `ru`, `original_kk`, `approved_kk`, `issue_type`, `context`, `glossary_terms`, `reviewer`, `status`.
- Для трёх кандидатов хранятся тексты, объяснения и решение: выбран один, написан свой вариант или все отклонены. Несогласие носителей записывается, а не скрывается.
- Из принятых строк создаются учебные искажения с известными типами ошибки. Реальные найденные ошибки хранятся отдельно от синтетических.
- Учебная, проверочная и финальная тестовая части разделяются по исходному ключу и близким шаблонам. Ни один вариант или искажение тестового ключа не попадает в обучение.
- Данные организатора и производные примеры остаются в игнорируемых Git приватных каталогах.

## Сигнал обучения и метрики

Детектор возвращает три статуса: `error`, `uncertain`, `no_issue`. Неуверенность видна в отдельной очереди, не считается доказанной ошибкой. Оценка детектора строится на человеческих метках: precision и recall по типам ошибок, а также доля строк, отправленных на ручную проверку. Синтетический тест показывается отдельно от реального.

Исправитель оценивается носителями по сохранению смысла, естественности казахского, игровому словарю и длине UI. Плейсхолдеры и ICU проходят обязательную программную проверку. Оценка языковой модели может помогать сортировке, но не служит эталонной наградой. Цель 90–97% указывается только вместе с названием метрики, размером и происхождением независимого теста.

## Ночная подготовка и утренняя проверка

Ночью: прогон ARB, технические находки, поиск терминов и повторов, предложения трёх вариантов, проверка плейсхолдеров и ICU, сортировка по уверенности, сбор таблицы `было → 3 варианта → причина → решение носителя`. Утром три носителя проверяют приоритетные смысловые строки и игровой сленг. Технические черновики тоже не получают флаг `reviewed_by_human=true` до реальной проверки. Пропущенный ключ сам по себе не даёт безопасного перевода.

## Сдача кейса

Сохраняются обязательные артефакты: CLI, `report.json`, HTML-отчёт, глоссарий, `intl_kk_fixed.arb` с отметкой каждой изменённой строки и описание методики. Перед сдачей запускаются тесты, аудит отметок и `flutter gen-l10n`. Метрики на скрытых ошибках организаторов не выдумываются.
